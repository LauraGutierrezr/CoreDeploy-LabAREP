De tu carpeta local a GitHub y a la instancia EC2

Los comandos exactos para subir el proyecto, probarlo localmente y dejarlo corriendo en el puerto 8081 de tu instancia EC2 (la misma del laboratorio de networking, si sigue activa). Marca cada paso a medida que lo completas.

PARTE 1

Subir el proyecto a GitHub

Partiendo del .zip que ya tienes descargado, con las 5 commits completas (esqueleto → framework → app demo → tests → deploy y README).

PASO 1

Descomprimir el proyecto

Abre una terminal en la carpeta donde descargaste el archivo:

unzip CoreDeploy-LabAREP.zip
cd coredeploy

Verifica que ves las 5 commits antes de continuar:

git log --oneline
PASO 2

Renombrar la rama y conectar el repositorio remoto

Tu repositorio en GitHub ya existe (CoreDeploy-LabAREP) y está vacío:

git branch -M main
git remote add origin https://github.com/LauraGutierrezr/CoreDeploy-LabAREP.git
PASO 3

Hacer push

git push -u origin main

Git te va a pedir usuario y contraseña. Usa:

  • Usuario: tu nombre de usuario de GitHub
  • Contraseña: un personal access token (no tu contraseña normal — GitHub ya no la acepta por HTTPS)
Si no tienes un token a mano: GitHub → Settings → Developer settings → Personal access tokens → Generate new token (classic), con permiso repo.
PASO 4

Confirmar en GitHub

Abre https://github.com/LauraGutierrezr/CoreDeploy-LabAREP y confirma:

  • Aparecen los archivos (pom.xml, src/, README.md, deploy/, docs/)
  • La pestaña "Commits" muestra las 5 commits, no una sola
  • El README se ve renderizado en la página principal, con el diagrama de arquitectura
PARTE 2

Compilar y probar en tu máquina

Antes de tocar AWS, confirma que el jar se construye y los tests pasan en tu computador.

PASO 5

Compilar y correr los tests

mvn clean package

Debe terminar en BUILD SUCCESS con algo como Tests run: 24, Failures: 0, Errors: 0. Guarda esa salida — es evidencia para el README.

PASO 6

Correrlo localmente

java -jar target/lambda-web-framework.jar

En otra terminal:

curl "http://localhost:8080/hello?name=Ana"
curl "http://localhost:8080/pi"

Y en el navegador: http://localhost:8080/ — prueba el formulario de saludo y el botón de π.

Para detenerlo (modo desarrollo, no en producción): curl http://localhost:8080/shutdown, o simplemente Ctrl+C en la terminal donde corre.

PARTE 3

Desplegar en EC2 (puerto 8081)

Por defecto asumimos que reutilizas la misma instancia EC2 del laboratorio de networking, en un puerto distinto (8081) para que ambos servidores puedan convivir. Si prefieres una instancia nueva, el paso 7 tiene la alternativa.

Antes de empezar: nunca subas tu .pem ni tus AWS access keys al repositorio — no los necesitas ahí para nada.
PASO 7

Abrir el puerto 8081 en el security group

En la consola de AWS → EC2 → Security Groups → selecciona el grupo de tu instancia → Edit inbound rules → Add rule:

TipoPuertoOrigenPara qué
Custom TCP80810.0.0.0/0 (o el rango que indique tu instructor)Acceder a esta aplicación

Si vas a lanzar una instancia nueva en lugar de reutilizar la del lab de networking, repite también la regla de SSH · 22 · My IP y usa el puerto 8081 como puerto de la app desde el inicio.

Ojo con las sesiones de AWS Academy: si tu Learner Lab se reinició (End Lab / Start Lab), es posible que se haya creado un security group nuevo sin esta regla — verifícala cada vez que retomes el laboratorio, es la causa más común de "la página no carga" aunque el servicio esté active (running) por dentro.
PASO 8

Conectarte a la instancia

chmod 400 ruta/a/tu-llave.pem
ssh -i ruta/a/tu-llave.pem ec2-user@TU-IP-O-DNS-PUBLICA
PASO 9

Copiar el jar y el servicio desde tu máquina

Desde la carpeta del proyecto en tu máquina (no dentro del SSH), con target/lambda-web-framework.jar ya construido:

./deploy/deploy.sh TU-IP-O-DNS-PUBLICA ruta/a/tu-llave.pem ec2-user

El script instala Java si hace falta, copia el jar, instala lambda-web-framework.service como servicio systemd en el puerto 8081 con APP_ENV=production, y lo arranca.

Si el script no se puede ejecutar (macOS, "operation not permitted"): suele ser el atributo de cuarentena del zip descargado. Prueba xattr -dr com.apple.quarantine . en la carpeta del proyecto. Si sigue sin funcionar, ejecuta a mano los comandos scp/ssh que están dentro de deploy/deploy.sh — son simples y no dependen del script.
PASO 10

Verificar desde dentro de la instancia

curl http://127.0.0.1:8081/pi
sudo systemctl status lambda-web-framework

Debe responder {"value": 3.141592653589793} y mostrar Active: active (running).

PASO 11

Verificar desde fuera (navegador)

Sal del SSH (o abre otra pestaña) y desde tu propia máquina:

curl "http://TU-IP-PUBLICA:8081/hello?name=Ana"

Luego abre http://TU-IP-PUBLICA:8081/ en el navegador y prueba ambos botones. Si se queda cargando, el problema casi siempre es el security group del paso 7 — vuelve a revisarlo.

PASO 12

Confirmar que /shutdown está desactivado

curl -i "http://TU-IP-PUBLICA:8081/shutdown"

Debe responder 404 Not Found — confirma que APP_ENV=production quedó bien configurado en el servicio.

PASO 13

Confirmar que sobrevive al cierre de sesión

Cierra tu sesión SSH por completo, espera medio minuto, y repite el curl del paso 11 — debe seguir respondiendo, porque systemd lo mantiene corriendo sin tu terminal abierta.

PARTE 4

Limpieza (obligatoria al terminar)

Para no dejar cargos ni recursos abiertos en AWS Academy.

PASO 14

Detener el servicio y liberar recursos

ssh -i ruta/a/tu-llave.pem ec2-user@TU-IP-O-DNS-PUBLICA sudo systemctl stop lambda-web-framework

Luego, en la consola de AWS:

  • Si ya no necesitas la instancia para nada más: EC2 → Instances → Terminate instance
  • Libera cualquier Elastic IP asociada (EC2 → Elastic IPs → Release)
  • Si la instancia se termina, revisa si el security group queda huérfano y elimínalo también
Con esto quedan cubiertos los dos laboratorios sobre la misma instancia (si la reutilizaste) — no hace falta repetir la limpieza por separado.
REFERENCIA

Problemas comunes

La página pública no carga pero curl local sí funciona: falta la regla del security group para el puerto 8081 (paso 7) — es, por lejos, la causa más frecuente.

«Permissions 0400 for key.pem are too open»: ejecuta chmod 400 tu-llave.pem.

El servicio no arranca tras systemctl enable --now: revisa journalctl -u lambda-web-framework -n 50 y /var/log/lambda-web-framework/server.log.

/shutdown responde 200 en vez de 404 en producción: el servicio no tiene APP_ENV=production — revisa deploy/lambda-web-framework.service en la instancia y reinicia con sudo systemctl restart lambda-web-framework.

Git pide credenciales y las rechaza: confirma que estás usando el token (no tu contraseña de GitHub) como password, y que el token no haya expirado.

EC2 Instance Connect dice "failed to connect": usa SSH por terminal con el .pem en su lugar — Instance Connect no siempre funciona si el security group restringe SSH a "My IP".

Referencia completa de diseño y decisiones en README.md del repositorio. Esta guía cubre solo la mecánica de subida y despliegue — súbela una vez y no hace falta volver a leerla, salvo que reinicies el proceso.
